# SuperCompany Coding PRD

## 1. 产品名称

**SuperCompany Coding**

## 2. 产品 Slogan

**Everyone can code. Everyone is a super company.**

## 3. 一句话定义

SuperCompany Coding 是一款模型无关的多 Agent 协同开发工具。用户只需要描述想做的产品，系统即可把需求拆解成任务，并调用不同模型驱动的 Agent 分别完成产品设计、架构设计、模块开发、测试、修复、代码合并和文档生成。

## 4. 产品边界说明

本产品**不局限于 Minimax 和 DeepSeek**。

Minimax 和 DeepSeek 只是当前用户已有 API Key 时的默认示例配置。产品架构必须面向所有模型开放：

- OpenAI / GPT 系列
- Anthropic / Claude 系列
- Google / Gemini 系列
- MiniMax 系列
- DeepSeek 系列
- Alibaba / Qwen 系列
- Moonshot / Kimi 系列
- ByteDance / Doubao / Seed 系列
- Zhipu / GLM 系列
- xAI / Grok 系列
- Mistral / Codestral 系列
- Cohere / Command 系列
- 本地模型：Ollama、LM Studio、vLLM、llama.cpp、LocalAI 等
- 任意 OpenAI-Compatible API
- 任意 Custom HTTP Provider

产品的核心不是“支持某个模型”，而是：

> 建立一套模型能力抽象层，让任何模型都能被接入、评估、路由、分配给合适的 Agent 岗位。

## 5. 背景与机会

AI Coding 已经从“代码补全”进入“Agentic Coding”阶段。但当前工具仍存在问题：

1. 多数工具默认绑定单一模型，用户难以发挥不同模型的优势。
2. 多模型 API Key 管理分散，切换成本高。
3. 单模型承担所有任务，容易出现上下文混乱、代码质量不稳定、成本不可控。
4. 普通用户仍然不知道哪个模型适合做产品、哪个适合写代码、哪个适合读长文档、哪个适合低成本批量任务。
5. AI Coding 工具缺少“组织化分工”——没有把模型抽象成可协作的虚拟团队。

SuperCompany Coding 的机会是：

> 把 AI Coding 从“一个助手”升级成“一个 AI 软件公司”。

## 6. 产品目标

### 6.1 用户目标

让用户可以：

1. 输入自然语言需求。
2. 配置任意模型 Provider。
3. 创建不同职责的 Agent。
4. 指定每个 Agent 使用哪个模型。
5. 让系统自动拆解任务。
6. 并行调度多个 Agent 开发项目。
7. 自动合并、测试、修复代码。
8. 输出可运行项目和交付文档。

### 6.2 产品目标

第一阶段目标：

- 做成 Windows / macOS 桌面 App。
- 支持任意 OpenAI-Compatible 模型接入。
- 支持 Minimax、DeepSeek、OpenAI、Claude、Gemini 的一方适配器。
- 支持用户自定义 Agent 和模型绑定。
- 支持一个小型项目从需求到可运行代码的闭环。

长期目标：

- 成为多模型、多 Agent 的 AI 软件开发操作系统。
- 用户像搭团队一样搭 Agent。
- 系统像项目经理一样调度模型。
- 让个人拥有公司级的研发生产力。

## 7. 目标用户

| 用户类型 | 需求 | SuperCompany Coding 的价值 |
|---|---|---|
| 非技术创业者 | 快速做 MVP | 把想法转成可运行产品 |
| 产品经理 | 把 PRD 变成 Demo | 不依赖完整研发团队也能验证需求 |
| 独立开发者 | 提升开发效率 | 多 Agent 分担架构、编码、测试、文档 |
| AI Coding 玩家 | 管理多个模型 Key | 统一 Provider 配置与模型路由 |
| 小团队 | 降低开发成本 | 形成 AI 虚拟研发团队 |
| 企业技术团队 | 引入多模型研发体系 | 按任务类型分配最合适模型 |

## 8. 核心功能

### 8.1 模型 Provider 配置中心

用户可以配置任意模型：

- Provider 名称
- Provider 类型
- Base URL
- API Key
- 模型名称
- 上下文长度
- 是否支持工具调用
- 是否支持 JSON Mode
- 是否支持多模态
- 是否支持流式输出
- 单价配置
- 并发限制
- 速率限制
- 可用性测试

用户只需要懂最基本的四项：

```text
名称 + Base URL + API Key + 模型名
```

高级配置由系统自动探测或使用默认值。

### 8.2 Agent 管理中心

用户可以创建 AI 团队：

- CEO / Orchestrator Agent
- Product Manager Agent
- Architect Agent
- Frontend Agent
- Backend Agent
- Data Agent
- Test Agent
- Debug Agent
- Security Agent
- Integration Agent
- Document Agent
- Cost Controller Agent
- Research Agent

每个 Agent 都可以：

- 绑定一个主模型。
- 绑定多个备用模型。
- 设置职责 Prompt。
- 设置可访问文件范围。
- 设置是否允许写文件。
- 设置是否允许执行命令。
- 设置成本上限。
- 设置失败降级策略。

### 8.3 模型能力矩阵

系统内置不同模型的能力标签，例如：

- 强推理
- 强代码
- 长上下文
- 低成本
- 快速响应
- 工具调用稳定
- 多模态理解
- 文档写作
- 中文能力
- 本地部署
- 企业 RAG
- 实时信息检索

系统基于能力标签为任务推荐模型。

### 8.4 任务拆解与调度

用户输入：

> 做一个桌面端候选人简历匹配工具。

系统输出：

1. 产品需求清单
2. 技术架构
3. 页面模块
4. 数据结构
5. 后端逻辑
6. 测试任务
7. 文档任务
8. Agent 分配方案
9. 模型调用预算

### 8.5 多 Agent 协同开发

支持四种模式：

| 模式 | 说明 | 适用场景 |
|---|---|---|
| 串行模式 | 一个 Agent 完成后交给下一个 | 强依赖任务 |
| 并行模式 | 多个 Agent 同时开发不同模块 | 前后端、文档、测试并行 |
| 评审模式 | 一个 Agent 写，另一个 Agent 审 | 重要代码、复杂架构 |
| 竞赛模式 | 多个 Agent 给方案，由 Judge 选择 | 技术选型、复杂 Bug |

### 8.6 代码工作区

需要支持：

- 文件树
- Monaco Editor
- Diff Viewer
- Git 状态展示
- 按文件接受 / 拒绝修改
- 按任务接受 / 拒绝修改
- 自动生成 commit message
- 回滚变更

### 8.7 测试与修复闭环

默认闭环：

```text
生成代码
→ 合并代码
→ 运行 lint / test / build
→ 捕获错误
→ Debug Agent 修复
→ 再次测试
→ 最多自动修复 3 轮
→ 生成交付报告
```

### 8.8 成本控制

支持：

- 项目级预算
- Agent 级预算
- 单任务预算
- 模型单价配置
- Token 使用统计
- 成本预估
- 低成本模式
- 失败升级策略

## 10. 关键用户故事

### 用户故事 1：配置模型

作为用户，我希望只填写名称、Base URL、API Key 和模型名，就能接入一个新模型，以便快速使用任何模型服务。

验收标准：

- 可以新增 Provider。
- 可以测试连接。
- 可以保存配置。
- API Key 不明文展示。
- 连接失败有明确错误提示。

### 用户故事 2：为 Agent 指定模型

作为用户，我希望给 Architect Agent 用 Claude，给 Backend Agent 用 DeepSeek，给 Doc Agent 用低成本模型，以便发挥不同模型优势。

验收标准：

- 每个 Agent 可绑定主模型。
- 每个 Agent 可设置备用模型。
- 执行任务时显示实际调用模型。
- 模型失败时可按策略切换备用模型。

### 用户故事 3：自动推荐模型

作为用户，我不一定知道哪个模型适合哪个任务，因此希望系统根据任务类型自动推荐模型。

验收标准：

- 系统根据任务类型展示推荐模型。
- 推荐理由可见。
- 用户可以覆盖推荐。
- 路由记录可追踪。

### 用户故事 4：完整开发闭环

作为用户，我希望输入一个产品想法后，系统能自动拆任务、写代码、测试、修复并输出可运行项目。

验收标准：

- 生成任务清单。
- 分配 Agent。
- 生成代码。
- 展示 Diff。
- 运行测试。
- 修复错误。
- 输出 README。

## 11. 非功能需求

| 类型 | 要求 |
|---|---|
| 性能 | 项目打开时间 ≤ 3 秒，小型项目任务拆解 ≤ 60 秒 |

| 兼容性 | 支持 Windows 10+、macOS 13+ |

| 指标 | MVP 目标 |
|---|---|
| 首次 Provider 配置成功率 | ≥ 80% |
| 首次 Agent 绑定成功率 | ≥ 80% |
| 首个项目生成成功率 | ≥ 50% |
| 自动修复成功率 | ≥ 40% |
| API Key 安全事件 | 0 |
| 单项目平均使用 Agent 数 | ≥ 3 |
| 单项目模型切换使用率 | ≥ 30% |

## 13. 产品原则

1. **模型中立**：不站队任何模型厂商。
2. **能力优先**：按任务能力选择模型，而不是按品牌选择。
3. **用户可控**：自动推荐，但用户永远可以手动指定。
4. **本地优先**：项目文件和 Key 默认本地保存。
5. **可解释**：每次选择某个 Agent / 模型都需要有理由。
6. **工程闭环**：生成代码只是中间过程，能运行才是交付。

## 18. 场景驱动 Agent 组织生成器

### 18.1 模块定位

后续核心发展方向是：用户不需要先手动搭建 Agent 团队，而是先给出业务场景，由 AI 自动预估需要多少智能体参与、每个智能体负责什么、每个智能体推荐使用哪个模型。

这意味着 SuperCompany Coding 的核心交互从：

```text
先配置 Agent → 再输入需求 → 执行开发
```

升级为：

```text
先输入场景 → AI 生成 Agent 团队方案 → 用户调整团队 → 执行开发
```

### 18.2 用户流程

1. 用户输入产品场景。
2. 系统识别产品类型、复杂度、隐私风险、技术栈和交付目标。
3. 系统生成推荐 Agent 团队。
4. 系统说明每个 Agent 的职责、推荐模型、推荐原因和预计成本。
5. 用户自由增删 Agent。
6. 用户自由修改每个 Agent 的职责和 Prompt。
7. 用户自由替换每个 Agent 使用的模型。
8. 用户确认后，系统将 Agent Team Plan 转成实际任务工作流。

### 18.3 输出内容

系统必须输出：

| 内容 | 说明 |
|---|---|
| 场景分析 | 当前需求是什么类型、复杂度如何、风险如何 |
| Agent 数量建议 | 推荐需要几个 Agent，哪些必需、哪些可选 |
| Agent 职责 | 每个 Agent 具体负责什么 |
| 模型推荐 | 每个 Agent 推荐使用哪个模型 |
| 推荐原因 | 为什么该 Agent 适合该模型 |
| Prompt 草案 | 每个 Agent 的系统提示词 |
| 权限建议 | 是否允许读文件、写文件、执行命令 |
| 成本预估 | 大致调用成本和高低配方案 |
| 风险提示 | 删除或合并某些 Agent 可能带来的影响 |

### 18.4 用户可控项

用户可以调整：

- Agent 数量。
- Agent 名称。
- Agent 职责。
- Agent Prompt。
- Agent 主模型。
- Agent 备用模型。
- Agent 执行顺序。
- Agent 文件权限。
- Agent 命令权限。
- Agent 预算上限。

### 18.5 产品原则

1. AI 负责预估和推荐，用户拥有最终控制权。
2. 普通用户可以直接接受推荐方案。
3. 高级用户可以像搭团队一样精细调控每个 Agent。
4. 模型推荐必须解释原因，不允许黑箱分配。
5. Prompt 默认由 AI 生成，但必须可编辑、可保存、可复用。

详细规范见：`SCENE_AGENT_PLANNER_SPEC.md`。

## 新增核心原则：自主项目交付，而不是手动点击 Agent

SuperCompany Coding 的主流程必须从“用户逐个手动点击 Agent”升级为“主控智能体自主交付项目”。

用户不是任务调度员。用户在产品中的角色更接近 CEO：给目标、定边界、定预算、看汇报、做关键决策、验收结果。

主控智能体 Orchestrator Agent 才是项目负责人，需要负责：

1. 根据用户场景预估需要多少 Agent。
2. 给出每个 Agent 的职责、模型推荐和 Prompt。
3. 让用户在启动前一次性调整团队配置。
4. 启动后自动分配任务、控制依赖、调度执行。
5. 自动收集各 Agent 产出。
6. 自动进行代码合并、测试、Debug、文档生成。
7. 按阶段向用户汇报项目状态。
8. 只有在高风险、超预算、范围变更、危险命令等关键节点才打断用户。

标准流程：

```text
用户输入场景
  ↓
AI 生成 Agent 团队方案、模型推荐、Prompt 草案、执行计划
  ↓
用户一次性调整 Agent / 模型 / Prompt / 权限 / 预算 / 自主模式
  ↓
用户点击启动
  ↓
主控智能体自动调度所有 Agent 完成开发
  ↓
主控智能体阶段汇报
  ↓
关键风险点请求用户决策
  ↓
自动测试、修复、集成、文档
  ↓
最终交付可运行项目
```

因此，任务看板和 Agent 面板是“观察与干预入口”，不是默认主流程。默认主界面应该是 **Project Command Center**，用户主要听主控智能体汇报。

详见：`AUTONOMOUS_DELIVERY_SPEC.md`、`ORCHESTRATOR_REPORTING_SPEC.md`。

## 25. 公司式 Agent 协作与可干预机制

### 25.1 产品形态修正

SuperCompany Coding 不是一个“手动点击多个 Agent 的工具”，而是一个“AI 软件公司”。

用户在产品中的角色是 CEO，不是项目执行员。用户只需要：

1. 给出项目场景和目标。
2. 确认 AI 生成的 Agent 团队方案。
3. 在关键节点听主控 Agent 汇报。
4. 遇到风险、超预算、范围变化时做决策。
5. 必要时暂停项目并微调团队。

日常推进由 Orchestrator Agent 负责。

### 25.2 新增核心体验

完整项目流程应为：

```text
用户给出场景
  ↓
主控 Agent 组织需求澄清会议
  ↓
AI 生成 Agent 团队方案、模型推荐、Prompt 草案
  ↓
用户一次性确认或调整
  ↓
主控 Agent 自动组织架构评审、任务分工、模块开发、代码评审、测试修复
  ↓
用户通过 Project Command Center 听阶段汇报
  ↓
用户可随时暂停，查看 Agent 内部讨论
  ↓
用户可修改 Agent 数量、职责、模型、Prompt、任务范围
  ↓
主控 Agent 重新评估影响后继续执行
  ↓
最终交付可运行项目和完整报告
```

### 25.3 Agent 内部协作透明化

系统必须展示 Agent 之间的工作协作，而不是只展示最终代码。

需要支持：

1. 需求澄清会议。
2. 架构评审会议。
3. 开发同步会议。
4. 代码评审会议。
5. Bug 复盘会议。
6. 冲突仲裁会议。
7. 决策日志。
8. 任务交接记录。

默认只展示主控 Agent 的阶段汇报，用户可展开查看完整 Agent 讨论。

### 25.4 随时暂停与微调

项目执行期间，用户必须可以随时暂停，并执行以下操作：

1. 新增 Agent。
2. 删除或禁用 Agent。
3. 修改 Agent 职责。
4. 修改 Agent 使用模型。
5. 修改 Agent Prompt。
6. 修改任务范围。
7. 修改预算。
8. 修改权限。
9. 回滚到上一个检查点。

暂停后，主控 Agent 必须先生成影响评估，再恢复执行。

### 25.5 成功标准

本能力完成后，用户应该感觉自己不是在操作 AI 工具，而是在听一个 AI 项目负责人汇报一支 AI 研发团队的工作。
